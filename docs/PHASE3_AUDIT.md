## 4. Missing capabilities (consolidated)

1. Git command layer: read-only `status`, `diff`, `log`, `ls-files`, `merge-base`, `show`, name-status,
   numstat, rename detection, conflict/merge-state reading, all with fixed argv and no shell.
2. Diff model: file → hunk → symbol, plus added/removed/renamed/deleted classification.
3. Dependency/impact graph with persisted nodes and edges, AST-backed for Python and JS/TS.
4. Risk scoring with per-factor explanation and honest "approximate, not proven probability" labels.
5. Regression test artifacts (Playwright, API, GraphQL, DB invariant, workflow, security) with a
   generation → validation → trusted lifecycle and execution history.
6. Historical knowledge retrieval that measurably changes mission selection, with tests proving it.
7. Plan-then-execute separation with a reviewable plan and an explicit approval gate.
8. Loopback dashboard with authentication and evidence browsing.
9. Local monitoring (schedules, due-run execution, pause/resume, missed-run honesty, alerts).
10. Terminal/desktop notifications with content redaction and external channels off by default.
11. Schema migrations (Phase 2 grew tables additively under a single `SCHEMA_VERSION = 1` with
    `CREATE TABLE IF NOT EXISTS`; there is no migration path or downgrade story).
12. Retention/disk controls for evidence (22 MB already, only `runtime/tmp` is auto-pruned per
    `core/shared/evidence.py:64`).
13. Two-token CLI command routing and consistent flags across Phase 1/2/3 commands.

## 5. Technical debt

1. **No migration framework.** `core/metadata/store.py:18` sets `SCHEMA_VERSION = 1`; schema is one
   idempotent script. Phase 3 adds at least 8 new tables; without ordered migrations the store
   cannot be upgraded safely or tested for upgrade.
2. **Regex-based intelligence.** `core/intelligence/mapper.py` and `rules.py` use text patterns.
   Adequate for the synthetic app; insufficient for Module C on real TypeScript codebases.
3. **Orchestrator is discovery-coupled.** `Orchestrator.plan_missions` builds missions from
   discovery + spec only. Impact-driven planning needs a source abstraction, otherwise Phase 3
   forks the orchestrator (highest regression risk for Phase 1/2).
4. **Unpersisted journeys.** `journeys` table has 0 rows; journeys are rebuilt in memory during
   verification (`verifier._attempt`). A generated Playwright/DB regression test needs the durable
   journey/mutation record Phase 2 never stored.
5. **Empty knowledge directories.** `intelligence/global-knowledge/`, `reusable-scenarios/`,
   `discovered-patterns/` are created but unused, so "two knowledge scopes" is currently a claim
   about directories rather than working retrieval.
6. **Tight browser budget.** Adversarial mode allows 8 sessions; the validated run used 7/8. Any
   Phase 3 browser-based regression suite needs its own budget class, not the shared mode default.
7. **Hand-rolled CLI parsing.** `cmd_phase2` reuses one parser for seven commands; Phase 3 needs
   subcommand groups, and bolting them onto the flat dispatcher will make `main()` untestable.
8. **Stale config fields.** `config/khunkhaar.yaml` still declares `project.phase: 1`; limits that
   matter at runtime live in `MODE_BUDGETS` code rather than config, so operators cannot tune them.
9. **No per-command authorization record.** `--yes` is an ephemeral flag; Phase 3's plan/execute
   split and monitoring need a durable authorization record per project/target.
10. **Evidence has no index.** Files live under `evidence/<phase>/<run>/` with paths embedded in
    findings; there is no evidence table to query for a dashboard, and no size accounting.
11. **`FUTURE_COMMANDS` is empty**, so removed stubs now return "unknown command" instead of a
    helpful message — a small UX regression worth fixing in the new CLI layer.
12. **Test fixtures are FastAPI-only.** Phase 2's synthetic app covers Python; Module C/D on
    TypeScript needs a second synthetic repo (already required by §16).

## 6. Integration risks

| Risk | Why | Mitigation baked into the plan |
| --- | --- | --- |
| Accidentally mutating a company repository | `git` writes (`stash`, `checkout`, `clean`, `index` updates) would alter the user's work | Allowlist of read-only git subcommands enforced in one module; tests assert `git status` is byte-identical before/after analysis; never pass a path outside the registered project root |
| Privacy breach through the dashboard | A local UI can silently become network-visible | Bind `127.0.0.1` only, refuse other interfaces, token auth, no CDN/external assets, startup prints the exact bind address; test asserts it is unreachable from a non-loopback bind |
| Scheduler pretending to run while offline | Directly violates §9 | `monitor run-due` executes the due set and records `missed` rows for past-due windows; a run is only recorded when the command actually started |
| Company data leaving the machine via GitLab API | §2 forbids unapproved egress | GitLab is opt-in, read-only, token by env-var *name*, host added to `netguard` allowlist explicitly, no comments/approvals/pipeline triggers anywhere in the code path |
| New parser dependencies break the pinned venv | Host is PEP 668 externally managed; Phase 1 pinned everything | Prefer stdlib `ast` for Python; propose `tree-sitter` + language grammars as an *approved, recorded* install, with a regex fallback that marks inferred edges lower confidence |
| Orchestrator refactor breaking Phase 2 | The engine is the only caller of agents/probes | Extend with an additional mission source; run the existing 167-test suite plus a re-run of the vulnapp scenario after each workstream |
| Dashboard/monitoring inflating budgets and disk | More browser sessions, more evidence | Separate budget class, retention policy with dry-run, disk guard in `--doctor` upgraded to warn at a threshold |
| LLM/agent-driven shell execution | §15 explicitly forbids it | No shell execution from agent output; every git/browser/API call goes through typed executors with fixed argv and allowlists |

## 7. Security and privacy posture (current vs Phase 3 §15)

Already satisfied and reusable: local-first execution, host allowlist + SSRF deny list
(`netguard`), redaction at the persistence boundary (`redaction`, `evidence.write_json` mode 0600),
credential-by-env-name profiles (`credentials.py`), SQL read-only guard and masking, filesystem MCP
roots and `deny_names`, secret-value ingest disabled, destructive API methods gated, project
isolation audit script, structured JSONL logs, disk check in `--doctor`.

Needs adding in Phase 3: path-traversal guard for project registration of company repos, durable
execution audit log per capability, dashboard access control, evidence retention policy, explicit
project authorization record, git read-only enforcement, notification content filtering.

## 9. Proposed Phase 3 implementation plan (summary)

Workstreams, each ending in executed tests, in dependency order:

1. **P0 — Foundations**: migrations framework, new directory tree, config keys, evidence index,
   CLI subcommand router (no behaviour change for Phase 1/2 commands).
2. **P1 — Module A**: read-only Git engine + `khunkhaar git status|analyze`.
3. **P2 — Module C**: dependency/impact graph (stdlib `ast` first, tree-sitter after approval,
   regex fallback) + risk scoring with explanations.
4. **P3 — Module B**: local-ref MR-style analysis (`--base/--head`, `--commit`, `--range`,
   `--working-tree`); optional read-only GitLab adapter behind config.
5. **P4 — Modules D + E**: regression test generation, validation lifecycle, execution history,
   knowledge retrieval feeding test selection.
6. **P5 — Module F**: `khunkhaar plan` → reviewable plan → `khunkhaar qa` with approval gate,
   resource monitoring, budgets per capability.
7. **P6 — Modules G + I**: local monitoring (`monitor set|list|pause|resume|run-due|status`) and
   terminal/desktop notifications.
8. **P7 — Module H**: loopback dashboard (projects, runs, findings, regressions, diff analysis).
9. **P8 — Acceptance**: synthetic TypeScript/Python git repository with the six required
   conditions, the 14-step end-to-end verification from §16, the negative scenarios, and Phase 1/2
   revalidation; then Phase 3 documentation set.

Full details, file lists, test matrix and approval gates: `PHASE3_IMPLEMENTATION_PLAN.md`.

## 10. Approval required before implementation

Three decisions change the architecture or the machine, so they are requested up front:

1. **Dependency approval**: install `tree-sitter` plus `tree-sitter-python`,
   `tree-sitter-javascript`, `tree-sitter-typescript` into `.venv` (needed for reliable
   function-level impact on TypeScript). Alternative: stdlib `ast` for Python and a labelled
   regex heuristic for JS/TS, with lower confidence.
2. **Approval gate placement**: whether `khunkhaar qa` must refuse to execute any plan that has
   not been reviewed with `khunkhaar plan --approve` (safer, adds one step), or keep the current
   `--yes` model for Phase 2-style scans and gate only Phase 3 impact-driven runs.
3. **Dashboard and monitoring defaults**: dashboard bound to `127.0.0.1` on a configured port with
   token auth and disabled by default until `khunkhaar dashboard start`; monitoring implemented as
   a due-run executor intended for the user's own cron/systemd-user timer (nothing installed
   automatically, no company infrastructure).

Phase 1 and Phase 2 remain untouched in behaviour; every workstream re-runs the existing 167 tests
before it is called done.
